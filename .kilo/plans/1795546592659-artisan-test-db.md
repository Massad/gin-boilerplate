# Base jetable artisan_test : les suites Go ne touchent plus la base dev

**Statut** : document prêt pour exécution. L'étape suivante est
l'implémentation T1-T8 (3 phases, § Phasage), du ressort d'un agent
d'implémentation ; chaque phase se ferme sur son jalon ; commit
uniquement sur demande explicite.

## Contexte

Faits établis le 24 nov. 2026 (le plan REDIS_DB
`.kilo/plans/1795535384311-redis-db-isolation.md` — isolation des index
Redis 1/2/3 — est implémenté et validé ce jour : `make test` et
`make e2e` verts, sessions dev intactes) :

- **`make test` purge la base dev** : `TestCleanUp`
  (tests/article_test.go, l. 907 ; DELETE à l. 910) exécute
  `DELETE FROM public.tenant` — balayage global sur `golang_gin_db` (la
  base dev pointée par `.env`) ; `TestIntDB` charge `.env` lui-même
  (godotenv.Load, l. 153) → un `go test` direct hors make écrit
  **aussi** la base dev aujourd'hui.
- Les suites `controllers` (auth_test.go) sèment/suppriment leurs
  propres lignes (ciblé, non destructeur global) mais s'exécutent sur la
  même base que `tests`.
- `cmd/e2edb` recrée déjà n'importe quelle base autorisée via
  `E2E_DB_NAME` — allowlist `^[a-z][a-z0-9_]{2,62}$`, `artisan_test`
  passe. Il purge l'index Redis nommé par `REDIS_DB` (garde D3 : refuse
  l'index 1 quand `REDIS_DB` n'est pas posé) ; gardes anti-DROP :
  cible == `DB_NAME`, `postgres`, `template*` refusés, identifiant
  quoté par pgx.
- Recette `test` (Makefile:61-67) : prérequis `services_up`, source
  `.env`, masquage MSYS du pdftotext xpdf (pdftotext embarqué de
  Git for Windows), `go test -p 1 -v -tags=all`.
- CI (ci.yml) : `DB_NAME: golang_gin_db` au niveau job (l. 50) ; l'étape
  « Configure disposable test services » (l. 64-74) crée la base puis
  migre en superuser ; le smoke test du binaire reste sur
  `golang_gin_db` ; le job ne définit **aucune** variable
  `E2E_DB_ADMIN_*` (sans elles,
  e2edb retomberait sur `DB_USER`/`DB_PASS` non-superuser).

**Symptôme** : chaque `make test` efface les tenants de dev.
**Bénéfice** : la base dev survit aux cycles de test ; le destructeur
global de `TestCleanUp` s'exécute sur une base jetable.

## Objectifs et hors-objectifs

**Objectif** : les suites Go (`tests`, `controllers`) s'exécutent
exclusivement sur une base jetable `artisan_test`, recréée et migrée à
chaque `make test` ; aucune suite n'opère de balayage global ni de
purge sur la base dev `golang_gin_db` — ni par `make test`, ni par
`go test` direct ; exception documentée : root `main_test.go` continue
d'écrire/cleanup sa propre ligne `admin_user` (opération ciblée, non
globale).

**Critère de succès** : un tenant marqueur inséré dans la base dev avant
`make test` — slug `dev-keep-marker` (choisi à dessein dans la table que
le balayage global de `TestCleanUp` vide : `tenant`, pas une table
épargnée) — subsiste après `make test` ET après `go test` direct : si
une suite revenait sur la base dev, le `DELETE FROM public.tenant`
effacerait le marqueur et le jalon échouerait au lieu d'être vert à tort.

**Non-objectifs** : modifier `cmd/e2edb` au-delà de sa documentation
(zéro changement de logique) ; toucher aux migrations ou à
`.env`/`.env_rename_me` (`DB_NAME` reste `golang_gin_db` : c'est la base
dev) ; modifier `make e2e` (déjà isolé via `artisan_e2e`) ; restaurer
les données dev déjà purgées par les cycles antérieurs (perte déjà
subie, non restaurée par ce plan).

*Risques et limites → § Risques / cas d'échec.*

## Décisions de design (fixées)

| Sujet | Choix |
|---|---|
| Répartition des bases | **`golang_gin_db` = dev** (jamais écrite par les suites), **`artisan_test` = suites Go** (jetable, recréée à chaque `make test`), `artisan_e2e` = cycle e2e (inchangé) — deux acteurs destructeurs (balayage global `TestCleanUp`, DROP/CREATE e2edb) ne partagent pas une base |
| Épinglage | `TestMain` de `tests` et `controllers` pose `DB_NAME=artisan_test` au niveau processus (symétrique exact de `REDIS_DB=2`) ; godotenv ne surcharge jamais une variable déjà posée → `TestIntDB` peut continuer à charger `../.env` pour l'hôte et les secrets sans risque de repli |
| Fail-closed | `artisan_test` absente → l'init des pools échoue explicitement (`database "artisan_test" does not exist`) ; jamais de repli silencieux sur la base dev |
| Réutilisation d'e2edb | Aucun nouvel outil : `E2E_DB_NAME=artisan_test REDIS_DB=2 go run ./cmd/e2edb`, préfixe limité à cette commande. Un seul outil = une seule source de vérité : les gardes existantes couvrent le cas (cible ≠ `DB_NAME`, allowlist, identifiant quoté, garde Redis D3) ; seule la documentation de l'outil se généralise |
| Recréation par cycle | `make test` recrée `artisan_test` à chaque exécution (DROP WITH FORCE + CREATE + migrations goose superuser), comme `artisan_e2e` ; le FLUSHDB de l'index 2 en préambule (porté par la même commande e2edb) donne un état Redis de départ déterministe — l'index 2 ne porte que les données des suites, jamais les sessions dev (index 1) |
| Littéraux | `artisan_test` et `2` écrits en dur (recette + TestMain + CI) ; leur accord est prouvé par l'assertion `current_database()` dans les suites (analogue de `Options().DB == 2` du plan REDIS_DB) |
| Preuve d'appartenance | `TestIntDB` et le setup de `controllers/auth_test.go` assertent `current_database() == 'artisan_test'` juste après l'init des pools, **avant** toute écriture (fixtures/seeds) |
| CI | 2 lignes ajoutées à l'étape existante « Configure disposable test services » (e2edb + migrate `artisan_test`) ; le smoke et le binaire restent sur `golang_gin_db` (l'étape de migration principale inchangée) |
| Périmètre non épinglé | `middleware` (Redis seulement : son `TestMain REDIS_DB=2` existant reste inchangé, aucun PostgreSQL dans le paquet), `internal/db/pool_test.go` (lecture seule non destructive sur la base configurée ; non épinglable : garde CI `git diff --exit-code internal/db`) et root `main_test.go` (upsert ciblé de sa propre ligne `admin_user`) restent hors épinglage — chaque cas nommé dans § Risques ; l'épinglage de `internal/testutil` (helper `current_database()` commun) est refusé par YAGNI jusqu'à un troisième paquet à épingler |

## Ce qui ne change pas

- **`cmd/e2edb` et `make e2e`** : identiques au paragraphe
  Non-objectifs — zéro changement de logique ou de recette.
- **`TestCleanUp`** (tests/article_test.go, l. 907 ; DELETE à l. 910) :
  le balayage global reste tel quel, précédé de la garde
  `current_database() == 'artisan_test'` (T5) — inoffensif sur la base
  jetable, fail-closed si un futur paquet non épinglé atterrissait
  dessus ; son bénéfice pour les `go test` directs entre deux
  provisionnements est conservé.
- **`.env`** : `DB_NAME=golang_gin_db` inchangé ; `make run` et le dev
  ne changent pas.
- **Migrations / db/queries / internal/db (généré)** : rien à toucher ;
  les migrations se rejouent à l'identique sur `artisan_test`
  (précédent éprouvé : `artisan_e2e` du cycle e2e — rôles idempotents,
  DO blocks de 000002).
- **Swagger** : aucune annotation → pas de `make generate_docs`.

## Alternatives rejetées

| Alternative | Motif |
|---|---|
| Export `DB_NAME` par la recette make seulement | contournable : un `go test` direct hors make charge `../.env` et écrit la base dev — exactement la classe de risque éliminée côté Redis par le `TestMain` |
| Nouvel outil `cmd/testdb` | duplique ~200 lignes + son fichier de tests ; deux outils pour « recréer une base jetable » = deux sources de vérité (rejet déjà acté pour le parseur dans le plan REDIS_DB) |
| Créer `artisan_test` seulement si absente | état initial incertain (résidus de cycles précédents, schéma dérivé) ; la recréation systématique est déterministe et identique au traitement d'`artisan_e2e` |
| `psql -c CREATE DATABASE` dans la recette | contourne les gardes de l'outil (allowlist, cible ≠ `DB_NAME`, identifiant quoté) ; le pattern du dépôt est l'outil Go |
| Truncate au lieu de DROP/CREATE | schéma jamais rafraîchi (dérive de migration silencieuse) ; le DROP WITH FORCE garantit un état vierge |
| Variable make `TEST_DB_NAME ?=` paramétrable | deuxième source de vérité face au littéral épinglé par `TestMain` ; un override divergent échouerait en base absente — fail-closed, sans bénéfice |
| Garde CI anti-littéral (`golang_gin_db` banni des fichiers Go non-commentés de `tests/`/`controllers/`, miroir du grep Redis) | rendrait durable la preuve one-shot du marqueur ; hors contrat de ce plan docs-only (élargirait T7 au-delà des 2 lignes) — déferré, adoption possible en suivi |

## Phasage

Trois phases ; chaque phase laisse le dépôt dans un état compilable :

1. **Phase 1 — provisioning + épinglage (T1-T7)** : e2edb (doc),
   recette `test`, `TestMain` ×2, assertions ×2, CI. L'épinglage sans
   provisioning rendrait `make test` rouge (base absente) : livrer d'un
   seul bloc. Jalon : phase 1 de la Validation verte.
2. **Phase 2 — preuves (§ Validation, jalons 1-4)** : marqueur dev,
   `go test` direct, régression `make e2e`, nettoyage.
3. **Phase 3 — documentation + mémoire (T8)**. Jalon : diff relu face
   à l'allowlist ; pas de commit.

### T3. `tests/main_test.go` — épinglage DB_NAME

```go
//go:build all

package tests

import (
	"fmt"
	"os"
	"testing"
)

// TestMain pins the disposable environment for the whole test binary: the
// Redis index 2 and the artisan_test database. The clients must be created
// while both are present in the process environment (godotenv never
// overrides an already-set variable), so no run can drift back to the dev
// database.
func TestMain(m *testing.M) {
	if err := os.Setenv("REDIS_DB", "2"); err != nil {
		fmt.Fprintln(os.Stderr, "error:", err)
		os.Exit(1)
	}
	if err := os.Setenv("DB_NAME", "artisan_test"); err != nil {
		fmt.Fprintln(os.Stderr, "error:", err)
		os.Exit(1)
	}
	os.Exit(m.Run())
}
```

## Risques / cas d'échec

- **`artisan_test` absente** (premier `go test` direct avant tout
  `make test`) : échec explicite à l'init des pools
  (`database "artisan_test" does not exist`) — voulu fail-closed ;
  documenté (AGENTS/README) ; tout `make test` provisionne.
- **`.env` avec `DB_NAME=artisan_test`** (configuration aberrante) : le
  provisioning e2edb refuse (cible == base applicative) — échec
  explicite, cohérent avec les gardes.
- **`make test` et `make e2e` concurrents** : DROP de bases distinctes,
  rôles idempotents, index Redis distincts, DO blocks exception-safes —
  sûr au niveau cluster, mais pas sérialisé au niveau commandes :
  `make test`/`make e2e`/`go test` direct lancés en même temps dans le
  même checkout écriraient les mêmes fichiers (install_goose → même
  GOBIN) ou se purgeraient mutuellement (FLUSHDB(2) d'un provisioning
  vs sessions d'un `go test` en cours ; deux `make test` concurrents
  se DROP mutuellement l'`artisan_test` ; `TestCleanUp` vide TOUTES
  les clés `user_sessions:*`/`admin:*` de l'index 2). Règle
  opérationnelle : un seul de ces cycles à la fois par checkout. La
  garde `TestCleanUp` est inoffensive sur la base jetable. Le DROP
  WITH FORCE déconnecte au passage des connexions obsolètes de la base
  ciblée.
- **root `main_test.go`** : sous `make test`/CI, upsert + cleanup de sa
