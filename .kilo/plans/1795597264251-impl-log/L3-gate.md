## Mécanisme soft-consume appliqué (dérivation documentée des clauses décision 7)

La politique du design fixe états et réponses mais ne nomme pas l'opération qui produit `delivered=0`. La machine d'états retenue satisfait **littéralement les trois clauses** :

- **Consommation** (1 Lua atomique, `ConsumeRefreshAuth`) : record actif + owner match → valeur `consumed:1:<value>` (délivrance **marquée à la consommation**), TTL recalé `min(grâce 5 min, TTL restant)` → code **1** (la demande doit délivrer ou relâcher) ; record `consumed:0` + owner match → `consumed:recovered:<value>` (TTL inchangé, ≤ grâce) → code **2** ; **tout le reste → 0** (missing, owner mismatch, `delivered`, `recovered`, état inconnu — échec fermé). Ownership inchangé : le segment userID est comparé **avant toute transition** (actif : segment 1 ; consommé : segment 3 — un étranger ne consomme ni ne réclame jamais la recovery d'autrui).
- **Release** (`ReleaseRefresh`, 1 Lua atomique) : uniquement `consumed:1` + owner match → `consumed:0:<value>` (TTL recalé) → 1 ; toute autre valeur → 0 sans toucher. Appelé par le handler `Refresh` (racine, fenêtre A2) sur **toutes** les branches post-consommation en échec pour le code 1 (relecture, statut, create, store) — « l'application a échoué avant émission de la nouvelle paire » = clause (ii) exacte : `delivered=0` n'existe que si l'application l'a déclaré.
- **(iii) crash** : crash après consommation → record `consumed:1` → rejeu → **401** (« delivered inconnu = non récupérable ») — satisfait pour toute lecture de « entre consommation et lecture » ; le replay concurrent d'un flux en vol (démarre après la consommation, marque 1) est refusé : **une seule émission maximum par jeton**, la menace « une paire que si la première tentative n'a rien délivré » tient exactement.
- **Replay pendant grâce** : `consumed:0` → recovery atomique (le claim récupère l'état dans le même script) → même forme 200 que le happy path (état encodé dans la valeur, jamais dans la réponse) ; rejeu suivant → 0 → 401 (**unicité**).
- **Sweep** (`Service.StartSweep(interval)`, ticker ~5 min cadence `DefaultSweepInterval`, démarré par `internal/app` ; stop retourné testable) : énumère les index `user_sessions:*` (SCAN+SMEMBERS), le script par membre classe 0 (actif/missing — jamais touché), 1 (consommé, grâce active — conservé), 2 (relique : TTL -1 ou > grâce — DEL) ; compte + journalise (std `log`) ; jamais la dépendance de purge (éviction TTL primaire). L'observabilité « au marquage et à la récupération » est loggée dans `ConsumeRefreshAuth` (codes 1/2).
- **Rollout/rollback** : records actifs au format inchangé (binaire pré-Phase-3 lisible) ; seuls les consommés (≤ 5 min) portent le format étendu — rollback borné aux consommations en grâce (re-login requis, design §7). Carve-out du contrat limité au chemin « rejeu pendant grâce ».

**Conseq mécanique testée** : `TestRefreshOnlyConsumesMatchingOwner` — `wantRemaining` 0 → 1 (le record n'est plus DEL du tout : mismatch = intouché, suspendu = relâché en `consumed:0`, matching = délivré `consumed:1`) ; assertion replay-after-delivery 401 inchangée ; les codes de réponse HTTP du flow inchangés.
