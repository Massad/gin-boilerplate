## What this proposes (FeatureRange — lines 1–158, whole document)

**Header (lines 1–4).** This document is titled "Migration incrémentale vers une architecture modulaire par domaine — Design" and is explicitly a split of a 268-line original plan (`1795597264251-architecture-modulaire-par-domaine.md`, judged too large for the egm-review cycle): it carries lines 1–116 and 261–268 of that original, while the execution plan (lines 118–259: "feuille de route Phases 0-8, proposition P0-P1, critères de sortie") lives in a sibling file, `1795597264251-architecture-modulaire-par-domaine-plan-phases.md`. **Préambule (lines 6–27).** The proposal targets a layout of `cmd/api/` (entrypoint + explicit dependency injection), `internal/platform/` (a transversal technical base), and `internal/modules/<domain>/` (handler / service / repository / dto / tests per domain). Every phase must leave `go build ./...`, `go vet ./...` and `make test` green, and no dependency upgrade is mixed in (go-redis/v7 and jwt/v4 stay as-is; a follow-up is possible). The **Problème** section: the API works but its wiring is global — pool singletons (`internal/db/pool.go:92-121`), a global Redis client (`db/db.go`), package-level `*Model` vars, and no constructor that injects dependencies; business logic lives in Gin handlers (Refresh in `controllers/auth.go:84-162`, Logout, admin Login); real HTTP wiring is pinned only by CI smoke and Playwright (`SetupRouter` duplicates `main.go`'s routes); and adding a domain touches four root packages with no verifiable import boundary. Not migrating multiplies manual wiring and isolation-regression risk with every future evolution (members/invitations, billing). **Objectifs**: testability (explicit DI, repository fakes, pure per-module `service_test.go`), a per-domain layout with import boundaries and an RBAC/members extension point, and an HTTP contract "inchangé au byte près" throughout, with build/vet/tests green at each phase. **Non-objectifs**: dependency upgrades (dedicated follow-up post-Phase 8), wired RBAC (only the extension point is delivered, not member/invitation routes), configurable CORS (only if a cross-origin case becomes real), refresh httpOnly (explicit backlog, breaking for the current token-in-JSON contract), homogenizing response-key case (`"Message"` vs `"message"`), and any HTTP behavior change.

**Décisions structurantes actées (lines 29–37; marked as user-validated).** Seven numbered decisions: (1) sqlc-generated code moves `internal/db` → `internal/platform/db` in **Phase 1**, with `sqlc.yaml`, `.mockery.yaml` and the CI check `git diff --exit-code` updated in the same commit; (2) `main.go` → `cmd/api/main.go` in **Phase 1**, with Makefile `run`/`e2e`, `swag init -g`, CI build, the `app/playwright.config.ts:51` webServer, and `main_test.go` all following in the same commit; (3) the middlewares `TokenAuth()`/`AdminAuth()`/`RequirePermission` live in the **`auth` module** (they carry domain policy), and "La plateforme n'importe jamais les modules (aucun cycle)"; (4) the identity split is 4 modules — `auth` (sessions/JWT, unified login, refresh, logouts), `user` (identity, register, user login), `tenant` (slug, provisioning), `admin` (backoffice, audit) — where `auth` defines the ports `UserAuthenticator`/`AdminAuthenticator` implemented by `user` and `admin` at wiring time, and `user`/`admin` consume `auth`'s `TokenService` "via une interface définie côté consommateur" (auth supplies the implementation, injected in `internal/app`) — no cross-module interface is defined provider-side, extended to technical services (2026-11-25); (5) route duplication is removed by a new package **`internal/app`** (an explicit composition root: `NewRouter`) imported by both `cmd/api` and the integration tests, so `SetupRouter` disappears and the HTTP suite pins the real wiring; (6) an absolute interdiction (2026-11-25): `*pgdb.Queries` never crosses a module boundary (neither as port parameter nor return type) — in-transaction inter-module exchange goes through an explicit Unit of Work (`pgdb.WithinTx`) and the narrow platform interface `pgdb.InTx`, and each module exposes its repositories under explicit consumer-side interfaces (`ArticleRepository`, `UserRepository`, `TenantRepository`, `TokenRepository`, …); (7) refresh tokens switch to "Soft-consume strict" (2026-11-25): no immediate deletion on consumption — a nullable `consumed_at` on the session record + a hash of the refresh token (never the plaintext token) + a 5–10 min grace TTL + a cleanup job; replay during grace → `401 invalid_grant` (or re-issuance if the security policy prefers it — a choice "figé en exécution, sous tests dédiés"); ownership semantics unchanged (`TestRefreshOnlyConsumesMatchingOwner` remains the safety net); the session incident stays observable for support; planned in Phase 3 (module `auth`), with a contract carve-out "cf. plan (Risques transverses)".

**Alternatives considérées (rejetées) (lines 39–44).** Four rejected options: a single big-bang move (rejects step-by-step revert/review; the incremental choice costs commit/branch discipline and 9 phases); a light root-package reorganization keeping `controllers/`/`models/` (brings neither an import boundary nor a domain layout); full hexagonal architecture with ports/repositories for every domain (rejected: a single-implementation repository only buys a test fake; instead, consumer-side interfaces are kept only where a fake is useful — `ArticleRepository`, `TenantProvisioner`, the `auth` ports — accepting sometimes thin `dto.go`/`model.go` files for uniformity); and middlewares in `internal/platform` (rejected: `TokenAuth`/`AdminAuth`/`RequirePermission` carry domain policy — claims, RBAC — while platform must never import modules nor duplicate their context contract; the cost is that root consumers route through `internal/app` during the transient Phase 3–6 window).

**§4 Layout cible (lines 126–149).** A tree shows the target: `cmd/api/main.go` (dotenv, flags, secrets, pools, redis, `app.NewRouter`, run); `cmd/e2edb/` unchanged; `internal/app/router.go` (`NewRouter(deps)`: route table + SPA/static/swagger/NoRoute); `internal/platform/{config,redisdb,db,middleware,validate,httpx,mocks}/` (the first five moved from current locations; `httpx` — responders, pgx→HTTP error mapping, `ParseUUIDParam` + pure tests — created in Phase 2); `internal/testutil/` unchanged; the module directories `internal/modules/{article,auth,tenant,user,admin,invoice}` (with `auth` documenting the context keys userID/tenantID/role; `tenant` holding slug + provisioning + backoffice data; `user` implementing `UserAuthenticator`; `admin` implementing `AdminAuthenticator`; `invoice` moved from `invoice/` in Phase 8); and `db/migrations/`, `db/queries/` unchanged as SQL sources. **The dependency rule**: `modules → platform` directly; `modules → modules` EXCLUSIVELY via consumer-side interfaces — the rule covers both families, which `internal/app` distinguishes at wiring time: orchestration ports (`auth`'s `UserAuthenticator`/`AdminAuthenticator`/`UserReader`; `user`'s tenant-provisioning port) and technical services (the `TokenService` port declared by `user`/`admin`, with the `*auth.Service` implementation injected; per-module repo interfaces). No cross-module interface is defined provider-side; `platform` never imports `modules` (absolute invariant for the whole migration); `*pgdb.Queries` never crosses a module boundary (decision 6: Unit of Work `pgdb.WithinTx` + narrow interface `pgdb.InTx`). **Transient window Phases 3–6 (décision A2)**: root↔module imports are tolerated in BOTH directions, only for code being migrated; the window closes in Phase 7 (root directories removed) and the prohibition is verified by the exit criterion (a `git ls-files` count = 0). `internal/app` and `cmd/api` are the only places that ultimately import everything.

## How the existing system works, per this document (DetailedRange = N/A)

DetailedRange = N/A — no detailed implementation-plan section (roadmap, phase-by-phase steps, or exit criteria) exists inside this document; that content was split into the sibling `…-plan-phases.md` file. Per this document, the existing system is a working Gin REST API with all wiring global in `main.go` (~230 lines) and no dependency injection: controllers hold empty structs reading package-level `*Model` vars, business logic (notably token refresh) lives inside handlers, sqlc-generated access code plus hand-written pool singletons sit in `internal/db/`, and two PostgreSQL pools (`app_admin` BYPASSRLS for platform operations, `app_user` + fail-closed RLS via `WithTenant` for tenant business) are backed by Redis JWT sessions. Routes are declared only in `main.go` and manually duplicated by `SetupRouter` in the integration tests, so real `main()` wiring is pinned only by CI smoke and Playwright; a minimal, tested-but-unwired RBAC and a 4-module identity surface (auth/user/tenant/admin) already exist and this migration would preserve them byte-for-byte.
