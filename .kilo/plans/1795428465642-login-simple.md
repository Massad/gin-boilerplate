## Overview

Implémente la vue de connexion de la maquette « Atrium » dans le frontend React `app/` : les 4 vues de `login.html` avec leur commutation, **sans le bloc SSO**. Un endpoint unifié `POST /v1/login` tente l'authentification utilisateur puis superadmin et renvoie une réponse typée. Après connexion, le superadmin est redirigé vers `/admin` et l'utilisateur tenant vers `/`, chacune des deux pages affichant un titre et une phrase de bienvenue au prénom et nom. Sessions persistées (localStorage / sessionStorage selon « Rester connecté »), refresh silencieux côté tenant. Tests unitaires Go et React, e2e Playwright sur une base dédiée **supprimée puis recréée à chaque cycle**, avec fixtures.

## The Problem

La plateforme expose des endpoints d'authentification fonctionnels (`/v1/user/login`, `/v1/admin/login`, `/v1/token/refresh`) mais le frontend est vide : `app/src/App.tsx` affiche un texte statique. Aucune interface ne permet de se connecter. Trois blocages concrets :

1. La maquette n'a qu'un formulaire email + mot de passe, alors que user et superadmin sont deux routes distinctes avec des tokens signés différemment.
2. La table `admin_user` ne stocke aucun nom (`db/migrations/000002_multi_tenant.sql`) et la réponse `/admin/login` ne renvoie que le token : la salutation « prénom + nom » exigée sur la page d'accueil superadmin est impossible en l'état.
3. Le token access tenant expire en 15 minutes ; sans gestion du refresh côté frontend, la session casse au bout d'un quart d'heure.

## Goals

*   Intégrer fidèlement la maquette complète (2 volets, 4 cartes commutées, responsive mobile), SSO exclu.
*   Développer `POST /v1/login` unifié : tentative user puis superadmin sur le pool admin, réponse discriminée par `kind`, erreurs 406 génériques (pas d'énumération de comptes), 403 tenant suspendu. `/v1/user/login` et `/v1/admin/login` restent inchangés.
*   Migration `000003` : colonne `name` sur `admin_user` + flag `-name` sur le CLI `-create-admin`, et identité superadmin (id, email, name) dans la réponse de login unifié.
*   Redirection après login : `superadmin` → `/admin` (titre « Admin » + « Bienvenue {prénom nom} ») ; `tenant_user` → `/` (même structure).
*   Persistance de session : réponse de login en localStorage si « Rester connecté » coché, sinon sessionStorage ; refresh silencieux sur 401 via `/v1/token/refresh` (tenant uniquement) ; admin (8 h, sans refresh) renvoyé au login ; gardes de routes par `kind`.
*   Tests unitaires Go (intégration tag `all`, testify + httptest, conventions AGENTS.md) et React (vitest + testing-library + msw).
*   E2E Playwright : à chaque cycle, suppression de la base de test précédente puis création d'une base neuve (`artisan_e2e`), migrations goose, fixtures superadmin + owner tenant, Redis db 1 purgée, serveur Go en single-origin sur le build vite ; scénarios superadmin, utilisateur tenant et identifiants invalides.
*   Design system : composant `AuthLayout` + stories ; réutilisation de Button/Field/Input/PasswordInput/Checkbox/Divider/ErrorBanner existants.

## Non-Goals

*   SSO (bouton et divider « ou continuer avec » masqués).
*   Vues secondaires fonctionnelles : « Mot de passe oublié », « Demander un accès », « Créer une organisation » restent statiques (bannière « fonctionnalité à venir » à la soumission) ; aucun câblage au register.
*   Endpoints `/me`, refresh admin, modification ou suppression des endpoints existants.
*   E2E dans la CI (local uniquement), CI e2e.
*   Stack de test Go (mockery, gofakeit, testcontainers, testfixtures) : traitée par le plan séparé `1795428465642-stack-test-go.md`. Ce plan est auto-suffisant avec testify seul.

## Open Questions

*   **Titre de la page d'accueil tenant** : « Tenant » retenu par symétrie avec « Admin » (le contenu est identique : titre + phrase de bienvenue). Libellé isolé dans une constante, ajustable à la revue en une ligne.

## Critical User Journeys (CUJs)

### CUJ 1 : Connexion superadmin

*   **Given** : base migrée, superadmin créé via CLI avec `-name "Prénom Nom"`, navigateur sur `/login`.
*   **When** : saisie email + mot de passe superadmin, « Rester connecté » décoché, soumission.
*   **Then** : `200` `kind=superadmin` avec `admin.name` ; redirection `/admin` ; contenu : titre « Admin » + « Bienvenue {Prénom Nom} » ; session en sessionStorage ; à l'expiration (8 h / 401), purge et retour `/login`.

### CUJ 2 : Connexion utilisateur tenant

*   **Given** : tenant actif avec un utilisateur (fixtures e2e), navigateur sur `/login`.
*   **When** : saisie email + mot de passe utilisateur, « Rester connecté » coché, soumission.
*   **Then** : `200` `kind=tenant_user` ; redirection `/` ; « Bienvenue {prénom nom} » ; session en localStorage ; F5 → session restaurée ; access expiré → refresh silencieux via `/v1/token/refresh` puis rejeu.

### CUJ 3 : Identifiants invalides

*   **Given** : navigateur sur `/login`.
*   **When** : soumission avec un mauvais mot de passe (user ou admin).
*   **Then** : `406` générique, bannière d'erreur visible « Adresse e-mail ou mot de passe incorrect… », aucune session créée, aucune indication du côté (user/admin) tenté.

## Technical Plan (Architecture)

### Backend

*   **Migration `000003_admin_name.sql`** (goose) : `ALTER TABLE admin_user ADD COLUMN name varchar NOT NULL DEFAULT 'Superadmin'` ; down : `ALTER TABLE admin_user DROP COLUMN name`. Table plateforme sans RLS — aucune politique à ajouter.
*   **`db/queries/admins.sql`** : `GetAdminByEmail` renvoie aussi `name` ; `CreateAdmin` prend un paramètre `name` (upsert idempotent conservé). `make generate_sqlc` (code commité).
*   **`models/admin.go`** : `Login` renvoie l'identité complète (id, email, name) ; `Create` accepte le nom.
*   **`models/login.go`** (nouveau) : `UnifiedLogin(form)` compose les deux chemins :
    1. `UserModel.Login` → succès : résultat `tenant_user` (user, tenant, tokens) ; `ErrTenantSuspended` : propagé tel quel (le 403 n'a pas à être masqué) ; tout autre échec :
    2. `AdminModel.Login` → succès : résultat `superadmin` (admin id/email/name, admin token via `CreateAdminToken`/`CreateAdminAuth`) ; échec : erreur générique unique.
    *Sémantique : le chemin user prime ; l'admin n'est tenté que si le chemin user échoue (sauf tenant suspendu). Un même email présent dans les deux tables ne peut pas sonder les deux mots de passe.*
*   **`controllers/auth.go`** : `AuthController.Login` — bind `forms.LoginForm`, `forms.Translate(err, forms.LoginMessages)` → 406, réponse `gin.H` discriminée :

```json
{"kind":"tenant_user","user":{"id","email","name","tenant_id","role"},"tenant":{"id","slug","name"},"token":{"access_token","refresh_token"}}
{"kind":"superadmin","admin":{"id","email","name"},"token":{"access_token"}}
```

*   **`main.go`** : `v1.POST("/login", auth.Login)` ; flag `-name` sur `-create-admin` (défaut `Superadmin`) ; `make generate_docs`.

### Frontend

*   Routeur TanStack **en code** (pas de plugin file-based, la dépendance existe) : `/login` public, `/admin` (garde `superadmin`), `/` (garde `tenant_user`) ; `beforeLoad` redirige vers `/login` si session absente ou `kind` incompatible ; session admin sur `/` et inversement → redirection vers la bonne page.
*   `app/src/lib/api.ts` : wrapper fetch `/v1` (same-origin), header `Authorization: Bearer`, extraction JSON + erreurs.
*   `app/src/auth/session.ts` : clé unique `atrium.session`, écriture localStorage (« Rester connecté ») ou sessionStorage, lecture avec repli sessionStorage → localStorage, purge.
*   `app/src/auth/AuthContext.tsx` : session au boot, login (stockage + navigation selon `kind`), logout (GET logout correspondant + purge), refresh sur 401 (tenant : une seule tentative via `/v1/token/refresh`, tokens remplacés ; admin : purge → `/login`).
*   `LoginPage` : `AuthLayout` + 4 cartes commutées par état local (`login | create | request | forgot`), liens et « Retour à la connexion » comme la maquette ; carte login → mutation react-query vers `POST /v1/login` avec validation zod (email, requis) ; bannière `ErrorBanner` (texte de la maquette) masquée à la saisie ; bascule œil via `PasswordInput` existant ; carte « Créer une organisation » : aperçu de slug côté client conservé ; les 3 vues secondaires affichent à la soumission « Cette fonctionnalité n'est pas encore disponible. » ; SSO masqué.
*   Pages accueil : contenu unique — titre (« Admin » / « Tenant ») + « Bienvenue {user.name} ».
*   `AuthLayout` au design system + styles `.shell`, `.brand-pane`, `.brand-hero`, `.brand-quote`, `.mobile-brand`, `.form-card` dans `atrium.css` + stories colocated.
*   Dev : proxy Vite `/v1` → `http://localhost:9000` ; e2e et prod : single-origin (le Go sert `app/dist`).

```text
Navigateur ──POST /v1/login {email, password}──▶ Gin AuthController.Login (pool admin BYPASSRLS)
                                                ├─ GetUserForLogin → user ? bcrypt ✓ → token user (claims tenant/role, Redis)
                                                ├─ user OK mais tenant suspendu → 403
                                                └─ sinon GetAdminByEmail → bcrypt ✓ → token admin (Redis admin:)
            ◀── {kind, user|admin, tenant?, token} ──┘
   ├─ stockage sessionStorage | localStorage (atrium.session)
   ├─ superadmin → /admin ; tenant_user → /
   └─ 401 → refresh silencieux (tenant) puis rejeu ; admin 401 → purge → /login
```

### E2E

*   `make e2e` orchestre à chaque cycle :
    1. `go run ./cmd/e2edb` — `DROP DATABASE IF EXISTS artisan_e2e WITH (FORCE)` puis `CREATE DATABASE artisan_e2e` via un DSN superuser (rôle de migration, cf. `make migrate_up`), **garde de sécurité : refus si le nom cible est vide ou égal à `DB_NAME`** ; `FLUSHDB` Redis db 1.
    2. Migrations goose épinglées sur `artisan_e2e` (CLI `$(GOOSE_BIN)` du Makefile).
    3. `go run . -create-admin -email ... -password ... -name "Prénom Nom"` avec `DB_NAME=artisan_e2e` (fixture superadmin).
    4. `pnpm build` (le Go servira `app/dist` en single-origin).
    5. Playwright : `webServer` lance le serveur Go (`DB_NAME=artisan_e2e`, port dédié `9100`), projet `setup` sème l'owner tenant via `POST /v1/user/register`, puis specs CUJ 1/2/3.
*   Prérequis locaux (identiques à `make test`) : PostgreSQL + Redis actifs, `.env` présent ; `pnpm exec playwright install` une fois.

## Alternatives Considered

### Fallback client user→admin (deux requêtes HTTP)

*   **Pros** : zéro changement backend.
*   **Cons** : double requête pour l'admin et pour les identifiants invalides ; logique de répartition éclatée côté client.
*   **Reason for Rejection**: Rejected by author — une seule requête et logique portée par le backend (endpoint unifié), comportement identique pour tout client.

### Fallback client admin→user

*   **Reason for Rejection**: Rejected by author — pénalise le cas majoritaire (utilisateurs tenant : 2 requêtes systématiques).

### Endpoints `/me` (`GET /v1/user/me`, `GET /v1/admin/me`)

*   **Pros** : identité toujours fraîche côté serveur ; moins de données stockées au navigateur.
*   **Cons** : deux nouvelles routes, contrôleurs, tests, Swagger ; complexité supérieure au besoin.
*   **Reason for Rejection**: Rejected by author — la persistance de la réponse de login suffit ; aucun endpoint supplémentaire.

### Session sans persistance (mémoire React seule)

*   **Reason for Rejection**: Rejected by author — un F5 déconnecterait ; incompatible avec « Rester connecté ».

### Carte login seule / login + register câblé

*   **Reason for Rejection**: Rejected by author — « intégrer l'ensemble de la vue » : les 4 vues de la maquette sont intégrées (seules les soumissions autres que login restent inertes), sans élargir aux flows register/forgot/request.

### E2E via testcontainers / E2E intégré à la CI

*   **Reason for Rejection**: Rejected by author — base dédiée locale supprimée puis recréée à chaque cycle (pas de dépendance Docker sous Windows, réutilise les outils épinglés) ; l'intégration CI est hors périmètre.

## Non-Functional Requirements

*   **Sécurité** : erreurs 406 génériques (pas d'énumération), identité du tenant uniquement dans le JWT signé, mot de passe jamais sérialisé (`json:"-"`), e2edb refuse de dropper la base applicative, `DROP` ciblé sur `E2E_DB_NAME`.
*   **Compatibilité** : `/v1/user/login` et `/v1/admin/login` inchangés (tests, smoke CI et consommateurs existants préservés) ; migration `000003` rétro-compatible (DEFAULT pour les lignes existantes) ; CLI `-name` optionnel.
*   **Rollback** : `make migrate_down` (goose down 000003) ; le frontend est un build statique déployé avec le binaire.

### Risques & garde-fous

*   `DROP DATABASE ... WITH (FORCE)` : cible exclusive `E2E_DB_NAME`, refus si vide ou égal à `DB_NAME` — la base applicative ne peut pas être supprimée par erreur.
*   Sémantique de repli : utilisateur existant + mauvais mot de passe → pas de tentative admin (pas de double sondage) ; documenté dans `UnifiedLogin`.
*   « Rester connecté » non coché + onglet fermé → session perdue par design (sessionStorage).
*   Le refresh n'est tenté qu'une fois (pas de boucle) ; en cas d'échec, purge et retour au login.
*   RLS : aucune table RLS touchée ; `admin_user` est une table plateforme.
